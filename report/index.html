The short-context ranking does not survive a 120K session

Adding multi-turn sessions that grow to ~118K tokens reorders almost everything. Gemma still leads. But Qwen3.5 — last on the 600-task suite — is the only model with no measurable long-context degradation at all, Mellum2 loses two thirds of its ability by 65K, and Qwen2.5-Coder cannot be given a 120K prompt on this card in the first place.

Read the two suites as two different questions. The 600-task suite asks whether a model can do the work. The 60-probe suite asks whether it still can after 118,000 tokens of conversation. A model can be good at one and bad at the other, and three of these four are.

The long-context suite: one growing conversation per category

Each of the twelve categories gets one conversation that grows to about 118,000 tokens. Conventions are stated once in the opening turns — the default branch is trunk, the CI runner is aer-linux-x64, every function returns a Result — and then never repeated. Five graded tasks are interleaved at increasing depth. All of them are graded the same way the 600-task suite is: code is executed, SQL is run, configs go through ssh -G, TypeScript must survive tsc --strict.

The padding is not filler noise. It is more of the same kind of material, and it carries deliberate near-misses: inventory blocks with ap-south regions and svc-* users, workflows on ubuntu-latest, legacy record types with ok-shaped fields. A model that pattern-matches the nearest plausible thing instead of recalling the stated one gets caught. Against lorem ipsum it would not.

Every probe is asked twice. Once at depth, and once with the filler removed and nothing else changed — same conventions, same prior turns, same worked examples. That control is what separates "cannot do the task" from "could no longer reach the fact", and it is the only number here worth trusting on its own.

Model answers never enter the history. After each probe the reference answer is inserted instead, so all four models see byte-identical context and one early slip cannot cascade through a whole session. The cost is that those references restate the conventions: at the deepest probe the nearest restatement is ~28K back, not 118K. So this measures holding a long session together, not pure needle distance. RAG is the exception — its answers restate nothing, making it the clean retrieval-at-distance signal.

How the failures happen: the model stops using the conversation

Counting only whether an answer uses the values the session established — ignoring whether the task passed — separates forgetting from ordinary error. Reverted means the answer contains a generic default the session had explicitly ruled out by name.

Gemma and Qwen3.5 hold their conventions at every depth. Across all 45 deep probes each, Gemma reverted to a generic default once and Qwen3.5 never did. Both sit at 8–9/9 in the shallow control too, so nothing about the task set explains Mellum2's collapse. Mellum2 reverted 10 times, and its adherence tracks depth almost monotonically.

The substitutions are the tell. At ~104K Mellum2 answered a request for July 2026 release tags with grep -E '^v[0-9]+\.[0-9]+\.7[0-9]{4}$' — inventing a semver scheme — where its own control produced git tag --list 'rel/2026.07.*'. On the CI probe it emitted runs-on: ubuntu-latest and actions/checkout@v3 after being told in the first turn that "ubuntu-latest does not exist in this org". On the React Native probe it dropped the theme hook and hardcoded marginBottom: 24. These are not degraded answers; they are competent answers to a different, generic question.

Qwen3.5's few long-context losses look different. At its shallowest rung it wrote an SSH block with ap-south, svc-scheduler and ~/.ssh/svc_search_ed25519 — every value lifted from a distractor in the padding rather than from the stated spec, while still getting ProxyJump, StrictHostKeyChecking and ForwardAgent right. It was not falling back on priors; it was picking the wrong nearby row.

Gemma gets 4.4× the usable context of Qwen2.5-Coder on the same card, and it is architecture that buys it, not quantisation. Gemma 4 uses sliding-window attention on most layers, so those layers never store a full-length KV. Qwen2.5-Coder is dense: 14B of AWQ weights leave 5.02 GiB, and 118K tokens need 7.03 GiB even at 4-bit TurboQuant KV. vLLM refused to start at 131072, 118784, 106496 and 90112, putting its hard ceiling at 84,880 tokens. Its two deepest rungs are not failures; they are 24 rejected HTTP requests.

Nominal context is not context in your code, either. The same byte-identical session came to 118,069 tokens under Qwen3.5's tokenizer but 129,008 under Mellum2's and 129,249 under Gemma's — about 9% more tokens for exactly the same text. Qwen3.5 is the efficient one here, not Mellum2 the wasteful one. That margin was enough to push three Mellum2 probes and two Gemma probes past a 131K window Qwen3.5 still had 13K of headroom in; all five were re-run with trimmed padding, and all five came back as real answers rather than rejections.

Qwen3.5's deficit is concentrated, not general

On eight of twelve categories Qwen3.5 is within 2–5 tasks of the pack. Its 46-task gap to Gemma comes overwhelmingly from two places: SQL 33/50 and GitHub 32/50, where every other model scores 39–43. Nothing else is anomalous — RAG is a perfect 50, React Native 48, JavaScript 47.

Those failures are its own, not shared difficulty. Qwen3.5 has 44 solo failures — tasks it alone got wrong — against 17, 19 and 22 for the others. It is making mistakes the rest of the field does not make.

Spot-checking confirmed they are genuine rather than harness artifacts. Token counts sit far below budget (43, 81, 21 against limits of 400 and 220), so nothing was truncated. On the top-product-per-category query it emitted LIMIT 1 OFFSET 0 instead of a window function — returning one row overall rather than one per category. That is a straightforward SQL error.

Worth keeping in proportion: it is a 9B model against 12B and 14B rivals, and it still clears 83%.

How Qwen3.5 was configured — and why it matters

It was run with thinking disabled, and that is not a neutral choice. Qwen3.5 reasons by default. At this suite's per-task token budgets it returned finish_reason=length with content=None — the entire 220-token allowance spent reasoning, no answer emitted. Scored as-is it would have collapsed to near zero for reasons unrelated to ability.

With enable_thinking: false the same prompt returns git reset --soft HEAD~1 in 8 tokens. Since the other three answer directly and the budgets assume that, thinking is off for this model only. This therefore measures Qwen3.5 in non-thinking mode; its reasoning mode is untested here and, given room to think, could plausibly score higher.

Fitting it at all took specific tuning. A default launch put weights at 12.72 GiB and left 0.24 GiB for KV — a ceiling of about 11.6K tokens. Two flags changed the picture: --max-num-batched-tokens 4096 caps the activation peak during profiling, and --limit-mm-per-prompt '{"image":0}' stops the profiler reserving vision-tower working memory that a text-only benchmark never uses.

With those plus 0.97 utilisation: weights 11.87 GiB, 2.61 GiB of KV, and the full 131,072 context at 1.26× concurrency. Ten times the usable cache from configuration alone.

That 0.97 setting did not survive contact with a long prompt. It served 600 short tasks without complaint and then OOMed and killed the engine on the first 118K request — the leftover 3% has to absorb the prefill activation peak, which scales with the prompt. The long-context runs use 0.93 with a 2,048-token prefill chunk, which still yields 135,168 KV tokens at 1.03×. The headroom cost almost nothing; not having it cost the whole run.

It fits 128K because it is a hybrid-attention model. Naive layer×head×dim arithmetic predicts ~64 KB per token at fp8, which would need 8 GiB for 128K and could never fit. Measured effective cost is about 18 KB/token — only some layers carry full KV.

That makes it, alongside Gemma and Mellum2, one of three models here serving the full 131K. Qwen2.5-Coder is the odd one out: even with YaRN rope scaling and 4-bit TurboQuant KV, its dense 14B weights cap it at 84,880 tokens on this card — which is what put its two deepest rungs out of reach.

The harness is tested harder than the models

Every task ships a reference solution; the build rejects any task whose own reference fails its own grader; and the complete reference set is then graded as a synthetic model. That oracle run scores 600/600, so a failure in a real run belongs to the model. Across 2,400 generations there were zero empty responses and zero request errors.

Ten harness defects were caught this way before any result was reported — six SQL tasks whose reference returned zero rows, twenty-one Git tasks with true checkers that any command would pass, a capture file polluting the git status it was asserting on, and an ssh -G boolean normalisation among them.

The most consequential was JavaScript. The first grading run reported 7/50, 0/50 and 2/50 — implausible for models that had scored 4/4 on JS at smaller scale, and contradicted by the oracle's 50/50. The prompt said "export with module.exports" without specifying the shape while the tests destructured {fn}; 141 of 150 answers used the other valid form. Grader tolerance was added, the oracle re-verified, and all runs re-graded from saved output. JS became 48/49/47 and the totals moved by more than 40 tasks each.

The long-context suite needed the same treatment, and its oracle also reports 60/60. Eight defects were caught before any score was reported. Two would have been charged to every model: a Python probe asserted 'itertools' not in src while reading a file that contained that assertion string — it could never pass — and a JavaScript probe expected [20000,30000,30000] from a function whose stated clamp caps the input at 5000. Depth calibration was wrong by up to 30%: a single chars-per-token constant put the deepest Bash probe at 152K against a 131K window, a hard reject. Per-category correction brought all twelve to within 0.3% of each other.

Two more were only visible in real output, not in the oracle. The Django session tells the model its models live in aerelith/work/models.py, so good answers opened with that import — which raised, because the harness only provided bench_app.models. The reference answers used the harness globals and never wrote the import, so the oracle passed while every real answer failed. A documentation probe demanded a literal E#### code the prompt had never asked for; all four models failed it identically, which is the signature of a bad probe rather than a hard one.

The most important fix was to the control itself. The first version stripped the earlier probe-and-answer exchanges out of the shallow run along with the padding — so the deep run had up to four worked examples the control lacked, and deep outscored shallow. Distance cannot do that. The control now differs from the deep run by exactly one variable: filler.

What this still does not show

The four did not run under equal conditions. Qwen2.5 needed YaRN and 4-bit TurboQuant KV to reach 80K; Gemma and Mellum2 ran native 131K on fp8; Qwen3.5 ran fp8 weights with fp8 KV at 131K but with reasoning disabled. Each of those choices costs something.

Single run at temperature 0, no repeats. Per-task variance is unmeasured. Gemma, Qwen2.5 and Mellum2 are separated by 16 tasks in 600 — close enough that a handful of coin-flips could reorder them. Qwen3.5's 30-task gap to third is the only difference here that is clearly outside the noise.

250 tasks are pattern-graded. They discriminate at this scale, but a regex cannot tell "correct" from "contains the right words". Treat the executed 350 as the harder evidence.

Category scores measure different things. Docs and React Native measure adherence to a described shape; Python, SQL, JS, TS, Django, Bash and Git measure whether the output actually runs and produces the right result.

The long-context suite is 60 probes, not 600. One probe is 1.7 points, so a 3-probe gap is not a result. Gemma's 46 and Qwen3.5's 45 are a tie. Mellum2's 16 and Qwen2.5-Coder's 24 rejections are not close calls.

It measures session-holding, not needle distance. Because canonical answers go into the history, the conventions are effectively restated every ~28K tokens. A suite that planted each fact exactly once and never referred to it again would be harder, and the ordering could differ. RAG is the only category here free of that effect.

Prefix caching was off for all four — vLLM disables it for these configurations, so every turn re-prefilled the whole conversation. That is identical across models and does not affect accuracy, but the wall-clock cost of a long session in this report is the worst case, not what a caching server would deliver.

Qwen2.5-Coder's long-context result is a hardware fact about this GPU, not the model. On a card with room for its KV it might hold 120K perfectly well — on the depths it could reach here, it did.

Recommendation

Gemma 4 12B QAT is still the default, and now for a second reason. It leads both suites — 546/600 short, 46/60 deep — is strongest in half the categories, has no weak domain, uses the least VRAM (8.3 GiB) and holds 372,010 KV tokens, 4.4× Qwen2.5-Coder's. It reverted to a generic default once in 45 deep probes. Its cost is unchanged: 18.4 tok/s, the slowest here.

Qwen3.5-9B is the one to reconsider. It finished last on short tasks and second on long ones, with the only perfect retention in the set and zero reversions at any depth. If your work is long agent sessions rather than one-shot prompts, the 600-task ranking is the wrong ranking to buy on. Two asterisks stand: it ran with reasoning disabled, and its short-context weaknesses (SQL 33/50, GitHub 32/50) do not disappear just because it holds context well.

Mellum2 is the clear loser here, and it is the reversal of the whole exercise. Third on short tasks and fastest at 26.1 tok/s, it keeps 34% of its ability at depth and is already down to 13/36 at 70K. For a model whose appeal was a long context window, having the window is not the same as using it. It remains a reasonable pick for short, high-volume work where its speed pays.

Qwen2.5-Coder is a capability question turned into a hardware question. It showed no long-context weakness on the depths it could reach — it just cannot be given more than ~85K tokens on a 16 GB card. If long sessions matter to you, that settles it on this machine regardless of how good the model is.

Shell, git and GitHub remain the weakest area across both suites. No model exceeds 46/50 on Bash or Git short, GitHub tops out at 41, and Git and SSH are also where the long-session substitutions concentrate — wrong branch, wrong runner, wrong host. In an agent that executes commands without review, that is where the risk sits, and depth makes it worse rather than better.
